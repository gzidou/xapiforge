@xapiforge/core — 场景清单（Scenarios） ​

这份文档是库设计/测试/文档的 single source of truth。

设计哲学：库设计应该覆盖所有这些场景。如果某个场景库没处理，标记 ⚠️ 或 ❌ 并在 BEHAVIOR-CONTRACT.md 同步。

v0.2 架构：库 = HttpClient + AuthService + createNet + middleware 链。 envelope 解包 / 业务错误判定归业务侧 middleware（如 createAbpUnwrapMw）。 库提供 Middleware 类型 + 内置 auth-mw / retry-mw / http-error-mw。

如何使用本表：

  1. 设计新特性：从表里找相关场景，加期待行为
  2. 写测试：每个场景一个 case
  3. 改行为：先改本表，再改代码
  4. 发现新场景：加到表里

覆盖范围：不限于ABP (.NET) projects。要枚举通用后端 + 典型边角 + 未来可能。

版本：当前实现（2026-08-04，data-or-throw + 结构化 ApiError）

Layer A：通用后端协议 ​

关键场景：ABP + Spring Boot + OAuth2 + RFC 7807 + GraphQL + 微信/钉钉 + 支付宝

v0.2 库的承诺：库不预设 envelope 形状。业务侧写 middleware（如 createAbpUnwrapMw）声明。 库内置 auth-mw（401 → refresh → retry）+ retry-mw（429 退避）+ http-error-mw（最终 validateStatus 校验 → ApiError）。

Layer B：网络层 / 边角情形 ​

当前库的承诺：fetch 失败、超时和主动取消抛 NetworkError，并分别使用 network / timeout / abort kind。 HTTP 状态失败与网络失败分开：前者抛 ApiError(kind="http")；429 内部重试耗尽后抛 ApiError(kind="rate-limit")。

#情形库行为
B1CORS preflight 失败 (OPTIONS 返 4xx)fetch 抛错 → NetworkError
B2HTTPS 证书过期浏览器拒绝，NetworkError
B3DNS 解析失败fetch 抛错 → NetworkError
B4TCP 连接超时fetch AbortController 超时 → NetworkError
B5服务端主动 close (ECONNRESET)fetch 抛错 → NetworkError
B6服务端关闭 keep-alivefetch 抛错 → NetworkError
B7响应 body 超大 (> 100MB)浏览器 OOM / 业务侧超时
B8gzip / br 解压失败fetch 内部错误 → NetworkError
B9chunked transfer 编码异常fetch 内部错误 → NetworkError
B10响应 Content-Type 与 body 不匹配guard-helpers.ts:parseJson 解析失败 → envelope=null
B11响应含 BOM (\uFEFF)JSON.parse 通常容忍，业务侧可处理
B12响应含 surrogate pair (emoji)UTF-8 标准，业务侧处理
B13响应 body 是 NDJSON (流式)库不支持，业务侧用 SSE/WebSocket
B14响应是 Server-Sent Events库不支持
B15请求 body 含二进制 (file upload)已支持（FormData）
B16请求 body 含 URL-encoded form已支持（URLSearchParams）
B17请求 body 是 stream库不支持
B18请求含 cookie业务侧手动塞 header
B19请求是 multipart 混合 text + file已支持（FormData）
B20CORS preflight OPTIONS浏览器自动发，业务侧不管
B21响应 Set-Cookie业务侧 token store 处理
B22SameSite cookie 跨域业务侧配置
B23重定向 3xxfetch 默认 follow，库不管
B24重定向循环fetch 默认最多 20 次 follow，错误向上
B25响应 WebSocket Upgrade库不支持
B26HTTP/2 pushfetch 内部处理
B27代理 407 Proxy Authentication Requiredfetch 抛错
B28业务侧 guard 抛错库向上传，⚠️ 待确认

Layer C：业务 envelope 变体（unhappy path） ​

v0.2 库的承诺：envelope 形状完全归业务侧 middleware（onResponse 阶段解包）。 库提供 Middleware 类型 + HttpResponse（含 bodyText / envelope / data）。

#envelope 形态例子业务侧实现
C1data 字段是 string{code: 0, data: "https://file.url"}unwrap: p.code === 0 ? p.data : p
C2data 字段是 array root{code: 0, data: [{...}, {...}]}同上
C3data 字段是分页 {items, totalCount}{code: 0, data: {items: [...], totalCount: 100}} (ABP PagedResultDto)同上 + 业务侧 unwrapAbpPaged<T>
C4data 字段是 null{code: 0, data: null} (DELETE)同上
C5msg 字段缺失{code: 0, data: ...} 老项目同上
C6code 字段类型是 string{code: "0", data: ...} (PHP 老项目)typeof p.code === "string" 兼容
C7code 字段是 boolean{success: true, data: ...}typeof p.success === "boolean"
C8响应里同时含 code 和 status{code: 0, status: "ok", data: ...}业务侧选一
C9envelope 是数组而非 object[{...}, {...}]unwrap: p => Array.isArray(p) ? p : []
C10envelope 嵌套 2 层以上{result: {inner: {code, data}}}unwrap 链式：p => p.result.inner.code === 0 ? p.result.inner.data : p

Layer D：鉴权 / token 场景 ​

v0.2 库的承诺：库提供 AuthService（单飞 + 窗口保护 + 超时）+ auth-mw（401 → refresh → retry）。 鉴权判定：HTTP 401 由 auth-mw 处理；业务 200 鉴权码由业务侧 middleware 抛 AuthError 触发 refresh。

#情形库行为
D1token 即将过期 (业务主动提前 refresh)库不感知；业务侧定时器触发
D2refresh token 也过期 (refresh 自己返 401)refresh 抛错 → AuthError + onAuthFailed
D3refresh 端点限流 (429)refresh 抛错 → AuthError + onAuthFailed
D4refresh 端点返 5xxrefresh 抛错 → AuthError
D5refresh 端点返业务 envelope 鉴权码refresh 抛错 → AuthError（业务侧 authRefresher.refresh() 自己解析）
D6refresh 端点 body 非 JSON业务侧 authRefresher.refresh() 自己处理
D7refresh 端点 timeoutwithTimeout 抛 NetworkError → 转 AuthError
D8token 含特殊字符 (+ / =)业务侧自己 encode；库透传 header
D9token 是 JWT 格式 (含 exp claim)业务侧 authRefresher.refresh() 可解析 JWT 提前 refresh
D10token 是 opaque (UUID)业务侧不管，库透传
D11双 token 体系 (access + refresh)业务侧 authRefresher.refresh() 返 access token；库只关心 access
D12单 token 体系 (长期不过期)业务侧 refresh 自己实现
D13多 tenant (ABP __tenant header)业务侧 per-request header；库不管
D14OAuth2 PKCE 流程业务侧自己处理 code_verifier；库不管
D15OAuth2 client_credentials业务侧 authRefresher.refresh() 自己实现
D16SAML 断言业务侧自己处理；库不管
D17API Key header业务侧每个请求塞 X-API-Key；库不管
D18HMAC 签名 (AWS SigV4 / 阿里云)业务侧每次请求签名；库不管

Layer E：生命周期 / 资源管理 ​

#情形库行为
E1createNet 重复调用✅ 工厂模式：每次返独立 client，无全局状态
E2createNet 后 tokenStore 引用变化✅ 工厂模式：client 持有 authService 引用，不变
E3createNet 后 baseURL 变化✅ 工厂模式：client 独立，需重新 createNet
E4业务页面卸载时 fetch 未完成业务侧 AbortController 主动 abort
E5业务页面卸载后 fetch 完成 (late response)库不管；业务侧 catch 后判断是否更新 state
E6浏览器 tab 切换到后台 fetch 是否继续浏览器行为；库不管
E7Service Worker 拦截 fetch业务侧配置 SW；库不管
E8浏览器离线 → 在线后重试业务侧自己实现重试逻辑
E9同一 endpoint 不同业务实例调用库不管；业务侧自己管理
E10多 tab 共享 token (localStorage)库不管；业务侧用 storage event 同步
E11多 tab 互斥 logout库不管；业务侧用 storage event

Layer F：错误传播 / Promise 行为 ​

#情形库行为
F1业务侧 catch 后 throw 一个新错误库不管；透传
F2业务侧 catch 后 await 其他 promise库不管
F3业务侧 try/catch/finally 中 finally 抛错库不管
F4业务侧 await Promise.all([net.request(...), ...])任一 reject → 整个 reject
F5业务侧 Promise.allSettled 中部分请求失败各自 catch；库不影响
F6业务侧 Promise.race 中第一个请求失败race reject；其他继续
F7AbortController.abort() 在 fetch 中途触发库支持（opts.signal）；抛 NetworkError(kind="abort")
F8用户主动取消请求同 F7

关键验证点 ​

  1. A14 业务 200 鉴权码（最关键）：业务侧 middleware 检测 code=40001 → 抛 RetryableError({ needsRefresh: true }) → createNet retry loop catch → authService.refreshIfNeeded() → 重发（新 token 由 auth-mw onRequest 注入）。✅ 链路完整
  2. A17 429 + Retry-After：retry-mw 抛 RetryableError → createNet retry loop 读取 Retry-After 退避。✅ 库内置
  3. A18 5xx + HTML：最终状态校验抛 ApiError(kind="http")，解析后的字符串 body 和 Response 均保留。✅ 库内置
  4. D2 refresh token 也过期：AuthService refresh 抛错 → onAuthFailed() 回调 → 业务侧跳登录。✅ 链路完整
  5. E1-E3 工厂模式：createNet() 每次返独立 client，无全局状态污染。✅ v0.2 核心改进

测试脚本 /tmp/test-a14.py，链路完整通过：

完整链路：

  1. localStorage.app_token = "biz-code-expired" → 下次请求 auth-mw 注入 Authorization: Bearer biz-code-expired
  2. mock-server /api/auth/biz-code-expired 返 200 + {code: 40001, ...}
  3. abp-unwrap-mw.ts 检测 code=40001 ∈ AUTH_CODES → 抛 RetryableError({needsRefresh: true})
  4. create-net.ts retry loop catch → authService.refreshIfNeeded() → token 更新为 refreshed-token
  5. auth-mw onRequest 用新 token 重发 → mock 返 200 + {code: 0, data: {...}}
  6. abp-unwrap-mw.ts 解 envelope → 返 data → 业务代码拿到 {ok: true, checked: "biz-code-expired path"}
